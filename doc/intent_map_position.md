# Intent Map：方案与产品定位

[← 返回项目 README](../README.md)

## 一句话定位

Intent Map 是面向 Agent 时代的软件创作与掌控工作台：它将业务核心物流动场景和约束沉淀为实现无关的分形内树，让人与 Agent 在合适颗粒度的树枝上达成共识，并按需、逐层、逐块地完成人可以理解、修改、接管或推倒重来的实现。

长期愿景是：**逐格掌控复杂度，协作构建超大规模软件。**

## 要解决的问题

Agent 可以快速生成大量功能、设计和代码，但生成速度已经可能超过人的理解速度。结果即使能够运行，也可能出现以下问题：

- 业务意图散落在聊天记录中，难以稳定继承；
- 一次输出范围过大，人无法理解完整实现；
- 代码存在，但没有工程师真正掌握它为何如此组织；
- 新的 Agent 会话需要重新推断上下文和既有决策；
- 用户难以判断应该在哪里介入、修改或接管；
- 多个 Agent 的异构输出继续发散，缺少统一的协作载体。

Intent Map 不以限制 Agent、消灭错误或证明业务判断正确为目标。用户可能有意选择非常规、不完整甚至表面矛盾的方案，以服务更深层目标。系统要保证的是：用户清楚当前确认了什么、掌控边界在哪里，并且能够低成本地修改、接管或重新生成。

## 核心策略：在合适的树枝上建立掌控边界

整个系统像一幅由许多方格组成的分形轮廓。树枝决定方格的颗粒度：方格太大时可以继续展开，足够清晰时便停下来确认。每次人工或 Agent 填充只聚焦于一个可理解的小方格。

```text
观察整体轮廓
→ 选择一根树枝
→ 缩放到合适颗粒度
→ 人与 Agent 达成局部共识
→ 手工、协作或代理填充
→ 回到整体观察
→ 不满意则局部修改或推倒重来
```

掌控不等于一次正确，而是始终具备以下能力：

- **可理解**：当前局部的目标、边界和产物在人可理解的范围内；
- **可修改**：人可以直接编辑 Agent 的输出；
- **可接管**：任何阶段都可以从 Agent 代理切换为人工实现；
- **可重来**：局部结果不理想时可以重新生成，不必推翻整体；
- **可聚焦**：只披露当前需要的复杂度，其余部分保持折叠；
- **可继续委托**：当前产物可以成为下一个 Agent 的结构化输入。

## 内树：稳定的业务语义核心

第一层聊天用于探索、提问、协商和产生候选方案；第二层内树用于沉淀值得保留的人机共识。

内树只描述实现无关的内容：

- 业务核心物流动场景；
- 参与者、输入与输出；
- 前置条件和结果；
- 正常流动与异常分支；
- 业务约束与人工决策点；
- 已经形成共识的局部边界。

内树不要求出现 React 组件、HTTP 路由、数据库表、编程语言或部署平台。它本身是独立而完整的产物，即使不存在任何外树或代码实现，也依然能够用于业务梳理、人机对齐、知识传递和后续协作。

内树也不是“正确业务”的裁判。系统可以呈现异常、矛盾和后果，但由用户决定保留、修改、暂缓或继续探索。核心标准不是正确性，而是意图是否被清楚表达，后续产物是否服务于当前确认的意图。

## 可选外树：按需披露和填充

外树是从内树的某个范围、以某种视角派生的可选投影。UI、DB Tables、API 和代码不是内树的组成部分，也不是每个项目必须走完的固定阶段。

```text
内树
├── 0..N 个 UI 投影
├── 0..N 个 DB Tables 投影
├── 0..N 个 API 投影
├── 0..N 个代码投影
└── 0..N 个其他领域投影
```

外树具有以下性质：

- 可以完全不存在；
- 可以只创建一种投影；
- 可以只投影内树的一根局部树枝；
- 同一树枝可以存在多个候选方案；
- 外树可以拥有与内树不同的层次和节点数量；
- 外树可以删除、替换或重新生成，而不伤害内树；
- Agent 输出不理想时，支持局部推倒重来或手工修正；
- 只有用户声明了具体投影目标和范围，才有必要讨论该投影是否满足当前目标。

系统采取乐观的创作模型：允许大胆尝试，不承担让所有外树永久自动一致的沉重责任。必要时提供来源提示和影响信息，最终由人选择保留、修正或重新生成。

## 八层渐进式创作模型

方案可以用八层描述，但这些层是可选的披露方向，而不是必须按顺序执行的软件生产流水线。

| 层级 | 含义 | 典型内容 |
|---|---|---|
| 第一层：聊天 | 探索空间 | 意图表达、追问、协商、候选方案 |
| 第二层：内树 | 掌控核心 | 业务核心物流动场景与约束 |
| 第三层：交互与契约 | 可选外树 | UI、DB Tables、API |
| 第四层：后端代码 | 可选实现 | 业务逻辑、数据访问、API 实现、测试 |
| 第五层：前端代码 | 可选实现 | 页面、组件、状态、交互、API 集成 |
| 第六层：外围系统 | 现实环境 | 身份、支付、消息、第三方服务、基础设施 |
| 第七层：分发 | 抵达用户 | 构建、部署、渠道、安装、升级和交付 |
| 第八层：分利润 | 价值闭环 | 收费、成本、结算、分成与激励 |

系统始终立足第二层。用户可以从内树向任意相关层逐步披露，也可以在某层停止、跳过或使用已有产物。每个局部均可选择：

- 完全手工实现；
- 人先写，Agent 补全；
- Agent 先写，人修改和接管；
- 完全委托 Agent 代理；
- 挂接外部已有实现。

## 小范围 Agent 输出

Agent 的任务应绑定到明确的树枝和目标层，而不是一次生成整个应用。

一个局部任务至少包含：

```text
来源树枝：当前工作的业务语义范围
目标层：UI / DB / API / 后端 / 前端 / 其他
目标：本次需要填充什么
边界：允许读取和修改的范围
输出：少量明确产物
检查：如何观察或试用本次结果
```

例如，为“确认订单”树枝生成 API 时，输出可以限制为一个接口契约、一组错误类型和少量示例；继续实现后端时，再生成一个 use case、一个 repository 接口和对应测试。每次变化保持在人能够完整阅读和手工修改的范围内。

分形结构支持按需缩放：如果一个任务仍然太大，就继续拆分树枝；如果边界已经足够清楚，就直接填充。超大规模软件由许多可掌控的局部组成，而不要求任何人一次理解全部细节。

## `.pip`：可掌控的 Agent 产物范式

Agent 原本可能输出聊天、文档、图片、Schema、API、代码、配置、构建产物和部署方案。`.pip` 不强制这些产物采用同一种内部格式，而是用统一的掌控结构组织它们。

```text
.pip
├── 内树：业务意图、核心流与约束
├── 外树：按需存在的各层投影
├── 产物：代码、资源、配置与可执行内容
├── 关系：产物所在的树枝和语义来源
└── 入口：供人或 Agent 继续聚焦与操作
```

因此 `.pip` 不只是压缩包或最终可执行文件，更接近 `.blend` 或 `.psd`：它既可以承载可运行结果，也保留继续理解和创作所需的结构。

`.pip` 同时承担三种角色：

1. **可执行或可分发的产物包**；
2. **人可以缩放和聚焦的掌控地图**；
3. **下一个人或 Agent 可以继续工作的协作上下文**。

由此，Agent 交付的不再是黑盒结果，而是自带理解入口、导航结构和接管边界的结果。任意 Agent 的发散输出可以收敛进 `.pip`，再从其中选择一根树枝继续创作。

## PIP MCP Server：Agent 的标准操作界面

为了经济地支持不同 Agent，Agent 不应各自解析和直接修改 `.pip` 内部格式。PIP MCP Server 作为统一操作层，为 Agent 提供局部、结构化、语义化的工具。

```text
Agent / Codex / IDE
        │ MCP
        ▼
PIP MCP Server
├── 打开和概览 .pip
├── 聚焦与读取树枝
├── 创建、更新和移动节点
├── 创建和填充可选投影
├── 挂载或修改局部产物
├── 导入现有项目和文件
├── 校验与导出 .pip
└── 输出局部上下文
        │
        ▼
      .pip
```

MCP 的核心不是暴露通用文件读写，而是提供围绕掌控边界的动作，例如：

- `open_pip`、`get_overview`；
- `focus_branch`、`get_branch`、`list_children`；
- `create_node`、`update_node`、`move_branch`；
- `create_projection`、`replace_projection_branch`；
- `attach_artifact`、`read_artifact`、`patch_artifact`；
- `import_artifacts`、`export_pip`、`validate_pip`。

Agent 只读取当前树枝所需的上下文，不必将整棵树和完整代码库装入会话。这可以降低 token 成本、减少上下文漂移，也让 `.pip` 内部格式能够独立演化。

## Intent Map 与 Agent 的双向关系

Intent Map 既是 Agent 的下游，也是 Agent 的上游。

作为 Agent 的下游，它：

- 接收一个或多个 Agent 的输出；
- 将发散产物收敛进 `.pip`；
- 允许人可视化比较、组合、修改和接管；
- 通过树枝组织多 Agent 在不同局部的工作结果。

作为 Agent 的上游，它：

- 通过 MCP 提供当前树枝的局部上下文；
- 给出当前意图、约束和操作边界；
- 提供编辑、填充、导入和导出工具；
- 将本轮结果变成下一轮 Agent 可继续消费的输入。

因此多 Agent 编排不一定依赖一个主动控制所有步骤的中央调度器。树本身可以成为编排结构：不同树枝交给不同 Agent、人工或外部系统处理，再统一收敛回 `.pip`。

```text
人选择树枝
→ Intent Map 提供上下文和边界
→ 人或 Agent 局部填充
→ 结果写回 .pip
→ 人观察、修改或重新选择
→ 下一轮继续展开
```

## 产品形态：软件开发的 Blender / Photoshop

Intent Map 在产品形态上更接近专业创作软件，而不是一次性 AI App Builder。

| Blender / Photoshop | Intent Map / PIP |
|---|---|
| 场景、画布 | 整棵分形地图 |
| 对象、图层 | 内树与可选外树 |
| 分组与层级 | 可展开的树枝 |
| 缩放、聚焦 | 选择合适颗粒度 |
| 选区 | Agent 可操作的局部边界 |
| 手工工具 | 人工编辑能力 |
| 生成式填充 | Agent 局部生成 |
| `.blend` / `.psd` | `.pip` |
| 插件 API | PIP MCP Server |
| 渲染与导出 | 构建、执行和分发 |

主要区别是：Blender 和 Photoshop 掌控空间与视觉复杂度，Intent Map 掌控业务意图、实现层次和人机协作复杂度。

## 核心价值：对复杂度的超强掌控力

Intent Map 的优势不是让 Agent 一次生成更多，而是让用户借助 Agent 完成更多时仍不失去掌控。

掌控力来自：

- **意图掌控**：内树保存不依赖聊天和具体实现的业务核心；
- **范围掌控**：树枝给出每次工作的局部边界；
- **颗粒度掌控**：复杂任务可以继续细分，直到人可理解；
- **披露掌控**：其他层按需展开，不强迫用户面对全部复杂度；
- **方式掌控**：人工、协作、代理和外部实现可以自由切换；
- **结果掌控**：输出可理解、可修改、可接管、可重来；
- **协作掌控**：多个 Agent 的产物统一收敛到 `.pip` 并可以继续消费。

当前价值主张是：

> 通过分形边界、逐层披露和局部填充，让人始终掌控 Agent 参与的软件复杂度。

长期愿景是：

> 将任意规模的软件分解为人可掌控、Agent 可执行的局部单元，以持续可理解的方式构建、分发并经营超大规模软件。

## 产品原则

1. **第二层优先**：聊天用于探索，内树用于保存稳定共识。
2. **内树独立**：没有任何外树时仍是有效产物。
3. **外树可选**：不存在固定、强制的生成流水线。
4. **用户决定颗粒度**：系统帮助缩放，不替用户决定必须理解到哪一层。
5. **Agent 局部工作**：单次输出保持在人可以完整理解和修改的范围内。
6. **乐观试错**：允许不一致和失败，以局部修正或重来代替沉重治理。
7. **人工与 Agent 平等**：每个局部都可以自由选择实现方式。
8. **外层不静默改变内树**：实现需要改变业务意图时，应回到相应树枝重新讨论。
9. **`.pip` 持续可编辑**：交付结果同时也是下一轮工作的输入。
10. **MCP 统一 Agent 接入**：编辑器服务人，MCP 服务 Agent，两者操作同一模型。

## 最小可行闭环

第一阶段不需要同时完成八层。最小闭环可以是：

1. 用户通过聊天描述一个真实业务场景；
2. 人或 Agent 将其整理为小型内树；
3. 用户选择一根树枝并调整到合适颗粒度；
4. 用户选择手工或 Agent 创建一种局部外树，例如 UI；
5. Agent 通过 MCP 读取边界、填充少量产物并写回；
6. 用户在编辑器中查看、修改、接管或局部重来；
7. 系统将结果导出为可再次打开和继续协作的 `.pip`；
8. 另一个 Agent 能从该 `.pip` 的指定树枝继续工作，而不依赖原始聊天。

这个闭环验证的不是“一键生成应用”，而是：`.pip` 是否真正让 Agent 的输出保持可视、可聚焦、可修改和可接管。

## 边界与长期方向

Intent Map 不承诺自动证明业务正确，也不需要保证所有外树永久一致。它提供的是一个低成本试错和持续掌控的环境。

超大规模软件开发仍会涉及跨树枝依赖、并行修改、权限、版本、组合和长期演化。这些能力应在最小闭环成立后逐步增加，不能以过早的通用架构牺牲当前可理解性。

最终，Intent Map 不是以代码替代人为目标，而是让人拥有一个能够观察、缩放和操纵软件复杂度的创作界面；`.pip` 让这种掌控力成为可保存、可传递、可执行、可由不同 Agent 持续操作的开放范式。
