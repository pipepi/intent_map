# Crypto CEX：软件开发掌控能力的实际案例

[← 上一篇：Software Authoring](software_authoring.md) · [返回总体方案](../intent_map_position.md)

## 定位

Crypto CEX 是使用 Software Authoring 节点预制件和模板地图构建的中心化数字货币
交易所案例，可作为 `crypto_cex.pip` 独立实现和分发。

它不是 Intent Map 的内置业务，也不是 Software Authoring 的通用模型，而是用于
验证“a2 通用编辑基础设施 + a3 软件创作扩展”能否支持人主导或可选 Agent 参与的
真实大型软件生产与反馈过程。

## 为什么选择交易所

Crypto 交易所同时包含大量相互关联又可以分形拆解的领域：

- 用户、身份、权限与合规；
- 充值、提现、地址与钱包；
- 账户、资产、冻结与账本；
- 订单、撮合、成交与清算；
- 行情、费率、风控和限额；
- 运营、审计、安全和异常处置；
- 高并发、外围系统和链上交互；
- 部署、分发、收费与利润分配。

它足够复杂，可以检验“在合适颗粒度的树枝上掌控复杂度”是否真正有效。

## 内树起点

案例首先描述与实现无关的业务核心物流动：

```text
Crypto 交易所
├── 用户进入并建立身份
├── 资产进入交易所
├── 用户表达交易意图
├── 订单进入撮合
├── 成交结果完成清算
├── 用户管理资产
├── 资产离开交易所
└── 平台收费并进行价值分配
```

每根树枝都可以继续展开。例如“用户表达交易意图”可以包含市场选择、订单条件、余额检查、资产冻结、订单接受或拒绝以及进入撮合等子场景。

## 局部投影示例

选择“冻结所需资产”后，可以按需创建：

```text
内树：冻结所需资产
├── UI：订单输入、余额和冻结反馈
├── DB Tables：账户、余额、冻结记录和账本
├── API：余额预检与下单契约
├── 后端：资产冻结事务和并发控制
└── 测试：并发下单不能超额冻结
```

这些外树全部可选。案例可以先只完成业务内树，也可以只针对高风险树枝披露更深实现。

## 案例边界

Crypto CEX 可以使用 Intent Map 的通用节点能力和 Software Authoring 的软件创作节点，但不得：

- 把交易所专用概念写入 Intent Map 内核；
- 把案例中的某种实现方案变成 Software Authoring 强制规则；
- 假设所有使用者必须借助 Agent；
- 为展示完整而强制生成所有外树；
- 用示例数据替代明确的业务约束。

## 实现映射

该文档应对应独立的案例目录或 PIP，包括：

- Crypto CEX 业务内树和示例数据；
- 按需生成的 UI、DB Tables 和 API 投影；
- 可选后端、前端和外围系统实现；
- 分发和分利润示例；
- 案例测试、演示脚本与说明；
- `crypto_cex.pip` 构建产物。

通用代码一旦被证明可复用，应向 Intent Map 或 Software Authoring 上移；交易所特有规则继续留在本案例。

## 验证目标

1. 验证 Intent Map 能承载深层、跨领域的分形节点应用；
2. 验证 Software Authoring 能把大型系统拆成可理解的小范围；
3. 验证用户可以逐层披露，而不必一次面对全部实现；
4. 验证人工和可选 Agent 可以在同一树枝上相互接管；
5. 验证外树可以局部修改、删除或重新生成；
6. 验证 `crypto_cex.pip` 可以被加载、编辑、运行和继续分发。

## 成功标准

案例成功不等于自动生成一个完整交易所，而是证明：面对真实复杂业务，用户能够随时定位当前树枝、选择合适颗粒度、理解局部产物，并决定继续人工实现、借助 Agent、手工修正或推倒重来。
